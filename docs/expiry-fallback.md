# Expiry fallback: design, decisions and operator manual

This manual describes source `05514a4b01a4b73ed33e238759f5f5520141f9e4`, compared with Second upstream `d96a7b3dc94b7e11322113b4c41284df036e0993`. Captaind freezes a complete, source-authorized allocation. Watchmand pays it in the transaction that consumes its physical backing, using its existing wallet for supplemental fees. Customer principal does not first pass through an operator payout wallet.

The route is disabled by default. It is not production-qualified. Complete conditional-source recovery, urgent deadline defenses, application behavior and operating readiness remain release requirements. Preparing matching executables does not establish those guarantees. See [Qualification limits](#qualification-limits).

## What changed

Upstream expires and recovers server-controlled outputs through Watchman. This fork adds immutable customer destinations, authenticated account-child attribution, source-specific ownership decisions, atomic allocation freezing, signed direct carriers, independent payment history, scheduled discovery and returning-client reconciliation. The retained legacy route swept first and then made a wallet-funded payout with proportional fees and a minimum. That route is dormant when direct settlement runs. Its rows and signed transactions cannot be ignored during a cutover.

| Decision | Current behavior and reason |
| --- | --- |
| D01 Identity | Register one immutable mailbox/account/destination binding before coin creation. Verify both full-field signatures and every exact account child. Metadata is attribution, not spend authority. |
| D02 Restoration | Native payout address is BIP84 external index 0. Reserve it on every load so seed restoration finds repeated receipts without scanning sparse Ark coin keys. |
| D03 Admission | Store proven origins with actual coin admission. Preserve registration, payment, settlement and source guards so a new cooperative right cannot race a frozen right. |
| D04 Ownership | Resolve all six source classes from authoritative facts. Missing paths, missing node evidence and a generic spent state do not establish operator ownership. |
| D05 Backing | Prove a complete disjoint cut through actual stored paths and current physical outputs. Reject missing siblings, alternatives, invented genesis and unrepresented value. |
| D06 Freeze | Commit immutable pay/forfeit/operator allocations together. Freeze is reservation, not a paid receipt. Refuse any unresolved retirement dependency. |
| D07 Allocation | Charge 1,000 sat once per actual recipient output. Preserve net principal; script-specific subdust groups forfeit instead of remaining below a minimum forever. |
| D08 Carrier | Consume authorized backing and preserve every recipient amount. Select only confirmed, trusted, unlocked Watchman supplemental inputs; retain exact output roles and signed fee bounds. |
| D09 Publication | Atomically store signed bytes, complete allocation mappings and the owning wallet stage. Recover uncertain commits with the same bytes and guards. |
| D10 History | Persist independent, identity-bound payment history before submission or adoption. Startup refuses forgotten, conflicting or inaccessible history. |
| D11 Scheduling | Captaind discovers complete cuts; Watchmand prepares or recovers complete frozen groups. Fair bounded passes preserve source-specific deferral reasons. |
| D12 Client status | Preserve pending value while frozen or unavailable. Adopt retirement only from authenticated status and an actual confirmed carrier winner; do not invent a payment receipt. |
| D13 Lightning | Durable preimage, actual collection, typed outgoing verdict and late-dispatch fence remain distinct facts. Silence is not final failure. |
| D14 Compatibility | Migrate compatible retained schema without losing history. Drain and reconcile incompatible identities or signed contracts before a fresh-state cutover. |
| D15 Financial controls | Bound signed quiet funding and direct carriers. Charge direct preparation against an independent lifetime allowance and preserve whole-input urgent cash. These controls do not constitute a global miner/router budget or restore disabled urgent reactions. |
| D16 Evidence | Models, test source, historical passes and build identity establish different things. Credit only actual execution at the stated source and boundary. |

## Customer identity and restoration

A version-3 `FallbackRecord` binds the chain genesis, mailbox public key, destination script and coin-account xpub. The mailbox key and ordinary child 0 of that account sign separate domain-separated hashes over the same full fields. Registration returns the canonical stored record. The portable record deliberately does not bind an Ark server key; using that identical authenticated binding at another honest server does not redirect funds. Server-specific address hints and payment-history identity remain separate. Repeating the same binding is safe; changing its script or account is refused. A randomized signature difference does not constitute a destination change. [Record format and verification][S01], [canonical database registration][S02].

The coin account is `m/350'/0'`; an ordinary child index identifies each coin key. An Ark address retains its existing blinded mailbox and adds one bounded child index. The server unblinds the mailbox and verifies that the exact child of its registered xpub equals the output policy key. It does not scan an arbitrary range, accept a hardened child or accept ambiguous duplicate hints. The same proof travels through board, arkoor, round and Lightning issuance. It is committed with the resulting source rows. [Address validation][S03], [origin admission][S02], [coin derivation][S04].

The backend receives public account information and signatures. It never receives the mailbox private key, seed phrase or customer coin private keys. Publishing an account xpub reveals its ordinary descendants and links activity. An account xpub plus one ordinary child private key can compromise that entire coin account. This account-wide exposure is an accepted design decision; the hardened boundaries do not expose the separate mailbox branch, BIP84 account or master seed merely from that pair. Protect child keys accordingly. This is not a claim that xpub disclosure is harmless.

For the native wallet, the fixed payout address is `m/84'/coin_type'/0'/0/0`, where `coin_type` is 0 on mainnet and 1 on other networks. Wallet state does not choose the lowest unused address. BDK reserves index 0 on every load. All later payouts to this wallet reuse it. Restore the same seed phrase with a normal BIP84 wallet and a correct chain/birthday; external gap 20 finds this index. A spendable confirmed on-chain receipt is separate from the Ark history debit. [Fixed derivation][S04], [BDK reservation][S05].

An external on-chain wallet is a separate integration seam. The application must supply an explicit immutable `fallback_spk`, and its `OnchainWalletTrait::is_mine` must recognize the script. Registration and reopen check that ownership. The Ark seed alone does not restore an unrelated external wallet. The external wallet must provide its own durable keys, descriptor and restoration procedure. No separate payout-only native wallet is created. [Wallet integration][S06].

On create or seed restoration without an authenticated local record, registration requires a reachable server. Authenticate its stored record and require its script to equal this seed's network-correct BIP84 external index 0 and its account xpub to equal this seed's coin account. Adopt that exact record; reject mismatches before overwriting local state. Opening an already authenticated local record does not make a server mismatch acceptable. An old offline-create option does not bypass registration. A lost reply can be retried against the durable local record. Sparse Ark recovery may receive a public child-index hint, but the client checks the returned VTXO ID and derives the full policy key from its own seed before storing it. This improves recovery without making a server hint spend authority. CLI `--fresh-mnemonic` explicitly treats a supplied new seed phrase as fresh and starts at the current tip; never use it to restore an existing funded seed. It conflicts with a recovery birthday. [Recovery validation][S07].

## Source authority and complete backing

All six sources remain in scope. The following describes the resolver, not a claim that every conditional route reaches payment automatically.

| Source | Rightful customer or explicit recovery evidence | Current boundary |
| --- | --- | --- |
| Registered VTXO | Current registered recipient, authenticated account origin and valid signed path. | Dependency-free complete cuts can freeze and pay. |
| Pending board | Recipient bound at genuine board co-sign; exact retained unsigned board reconstruction and actual funding output. | Abandonment before registration is supported. Unconfirmed, spent or invalid funding defers. |
| Unregistered output | Owner of its actual single-input parent, with the stored parent-spend association. A recipient hint alone does not transfer the entitlement. | Actual single-parent arkoor input-owner allocation is covered. Missing ancestry defers. |
| Collected Lightning receive | Immutable granted recipient, durable preimage **and** authoritative collected subscription. | A genuine externally collected receive before cooperative claim commit can freeze for the original recipient. This proof is freeze-only; later claim/output boundaries still need their own evidence. |
| Safe failed-send refund | Original sender, typed outgoing failure evidence, expiry/retry/dispatch fence, no authoritative preimage or completed attempt, and complete associated grant retirement. | Mixed verdicts preserve dependencies. The zero-grant cancellation path is supported under actual incoming-node cancellation; full-grant reconciliation remains required. |
| hArk/unclaimed replacement | Bound recipient, issued replacement, exact signed association and complete original/replacement retirement closure. | Completed contracts and proposals have source checks. Unfinished originals and conditional cross-tree closure defer; they are not independently finalized. |

Operator recovery requires positive evidence: exact unspendable round padding, a genuinely unused pool allocation, a completed and associated forfeit contract, a paid outgoing send, or a canceled unpaid receive whose collection and grant conditions are closed. Amount, missing ownership, timeout alone, blanket `Spent`, an unconfirmed foreign spend or unavailable nodes do not justify taking customer funds. Offboard-forfeit and unresolved external-preimage/cancellation cases remain separate required reconciliation classes. [Authoritative resolver][S08].

The `v_frontier_ownership_totals` reporting view classifies an unclaimed leaf as operator-owned only when its complete serialized policy matches the known round-padding policy. It does not exclude a customer's liability merely because its amount is 330 sat. This corrects padding inflated as customer-owned in the old report; the view is still a reporting projection, not proof that an entitlement has settled. [Canonical view](https://github.com/BullishNode/abandon-ship-bark/blob/05514a4b01a4b73ed33e238759f5f5520141f9e4/server/schema.sql#L1428), [compatible view migration](https://github.com/BullishNode/abandon-ship-bark/blob/05514a4b01a4b73ed33e238759f5f5520141f9e4/server/src/database/migrations/V70__expiry_obligations.sql).

The source inventory is an anchor superset, not proof that every row is a terminal. Geometry follows actual encoded paths from actual funding through each physical root. It accounts for every sibling and exact P2A residual, including zero-valued residuals. Alternative transitions, ancestor-and-descendant terminals, missing paths, duplicate roots, extra funding and unrepresented fees refuse the whole cut. Signature, source ownership, maturity and retirement checks remain separate from this geometric proof. [Snapshot and partition][S09].

The guarded Server freeze API obtains the current Core tip and funding facts internally. It holds sorted payment guards and `VtxosInFlux` through database commit, then settlement/carrier locks and ordered source-row locks. It rechecks inventory, ownership and source facts under those guards. Immediately before freezing it uses `gettxout(include_mempool=true)` and verifies the exact script/value, active tip, confirmation, coinbase maturity, server signer and clause maturity. A mempool spend refuses freezing. No caller can supply a pretend paid/canceled fact or an arbitrary tip. [Guarded freeze][S10].

For zero-grant intra-Ark cancellation, upstream setup/claim deadlines and absence of a preimage are necessary but insufficient. The actual owning hold node must report `Cancelled`; accepted partial setup may otherwise leave incoming money live. Cancellation closes later preparation under the same payment/settlement/source guards before the sender freezes. Paid, pending, unknown, missing and unavailable node states wait. If a preimage or collection wins first, the sender is never refunded. Existing full-grant conditional dependencies are not removed by this special case. [Cancellation boundary][S10], [outgoing evidence][S11].

## Allocation, fees and dust

A complete freeze writes each allocation's gross amount, source evidence, exact owner/script, disposition and full retirement set. Its canonical identity includes chain and server identity. A retry must read back identical fields; it cannot append a payable prefix or reassign principal. Competing registration, spends, claims and forfeits check frozen IDs and retirement roots. No ordinary source row is marked paid merely because it froze. [Freeze storage][S12], [admission fence][S13].

Within one frozen group, positive customer leaves with the same actual destination script form one recipient output. The output fee is exactly **1,000 sat**, independent of miner feerate or output weight. Native `VtxoId` ordering assigns the deduction without negative amounts or overflow: compare its internal 36 bytes, consisting of the transaction hash bytes followed by the little-endian output index. Displayed outpoint strings have a different order. A later independent group paying the same address can incur another fee; there is no promise of unlimited cross-group consolidation.

If the positive net after that fee is at least the script's standard non-dust value, pay it. If not, create no customer output, charge no output fee and record the full gross as forfeited. There is no configurable net minimum or permanent retained-small-balance category. For native P2WPKH, gross 1,294 sat pays 294 sat and charges 1,000; gross 1,293 sat forfeits 1,293 and charges zero. This uses the library's standard script threshold, not a claim of qualification under arbitrary custom Core dust policy. A frozen forfeit is still awaiting physical retirement. [Exact allocator][S14].

Let `B` be backing value, `P` recipient outputs, `W` supplemental Watchman inputs, `O` operator surplus, `C` Watchman fee change and `M` actual miner fee. The signed carrier enforces:

```text
B + W = P + O + C + M
funding_subsidy = W - C = max(M - (B - P), 0)
```

The builder preserves `P`. It can use flat charges, forfeits and explicit operator principal within `B-P` before drawing supplemental funds. It refuses an unaffordable closure rather than reducing recipients or splitting away unresolved branches. Omitted dust can increase the actual fee and is included in the signed-fee check. [Carrier construction][S15].

These are two different ownership roles: **fee inputs and `C` belong to Watchman**, while **`O` goes to configured `sweep_address`**. That address can belong to the Rounds wallet. The builder verifies that fee change is Watchman-owned and that `W-C` equals the recorded subsidy. It does not assume operator surplus replenishes Watchman. There is no dedicated payout wallet. The fee ceiling and the whole-input cash floor described below enforce different constraints. Count transfers between operator wallets once in consolidated accounts. [Enforced output roles][S16].

Direct carriers require a positive configured feerate ceiling, an absolute `max_miner_fee`, actual signed weight no greater than 400,000 WU, confirmed/trusted/unlocked supplemental inputs and complete allocation mappings. Quiet round and pool funding also check the actual signed child fee, including unconfirmed-ancestor subsidy and dust, before reservation or exposure. A capped estimate alone would not provide that guarantee. The urgent funding path remains distinct. The direct ordinary budget and cash floor below do not establish a global cumulative fee budget or qualification of urgent reactions alongside direct scheduling. [Signed quiet ceiling][S17], [runtime selection][S18].

## Direct ordinary allowance and urgent cash

`OrdinaryFeePolicy` declares `ordinary_budget_sat`, `external_future_reserved_sat`, `urgent_reserve_sat` and an optional `opening_sha256`. Captaind installs it during fresh creation; Watchmand must load the identical immutable policy before recovery and admin readiness. Defaults are 60,000 sat ordinary allowance, a fixed 20,000 sat prospective partition for costs outside this signer, and a 15,000 sat urgent cash floor. These amounts are defaults, not a capital model or a production recommendation. [Policy and durable ledger][S35], [startup load][S31].

Before signing a new ordinary carrier or replacement, reserve its entire configured `max_miner_fee` in the independent append-only ledger and fsync it. Failed attempts and confirmations do not replenish this allowance. Replaying exact retained bytes does not reserve again. Opening native costs, opening external costs, the fixed future partition and all subsequent ceiling reservations must fit the ordinary allowance. Startup checks the authenticated original history prefix and coverage of every retained signed version. An exhausted allowance defers new ordinary preparation while preserving existing bytes, obligations and reservations.

Before construction and after supplemental input selection, require enough **unselected whole confirmed, trusted, mature and unlocked Watchman UTXOs** to meet `urgent_reserve_sat`. One large UTXO cannot serve both roles; unconfirmed change and reserved inputs do not meet this floor. This is cash isolation for ordinary direct construction. It neither proves an urgent claim will succeed nor maintains an urgent-spend debit ledger. [Carrier cash checks][S15], [eligible wallet coins][S36].

The allowance wraps ordinary direct-carrier preparation only. Rounds, pool issuance, offboards and CLN router/wallet spending do not share a native cumulative debit ledger. The external partition is a fixed reservation, not an interceptor for those spenders. Their independent enforcement and reconciliation remain operating requirements. Per-payment CLN routing caps and signed round/pool ceilings must not be reported as global budget enforcement. The direct runtime still bypasses legacy urgent claim/progression handlers; this is a release blocker for workloads relying on those defenses. [Current reaction selection][S37], [round funding][S38], [pool funding][S39], [outgoing payment caps][S40].

For compatible retained direct history, install an independently authenticated, create-new adoption opening while financial writers are stopped. Bind the exact network, genesis, server key, complete original signed-history prefix, original native fees, external fees and accounting-receipt digest. Preserve every old history byte and carry all costs and still-reserved outside costs once. A digest alone does not authenticate the external journal. The source has no general adoption command: use a reviewed procedure that checks the actual retained transactions and accounting sources. Do not run fresh initialization over existing history, rewrite the opening, truncate the ledger or change policy to refill the allowance.

Back up `ordinary-fee-policy.json`, `ordinary-fee-opening.json` and `ordinary-fee-budget` with the independent payment history. Missing, noncanonical, changed, torn, exhausted or concurrently owned history refuses the applicable operation. Ordinary refusal is not customer forfeiture. Increasing an allowance or cash floor requires explicit policy and qualified adoption work; editing the configuration alone is refused.

## Durable publication and recovery

Watchmand hydrates the union of fee-input reservations from every retained carrier version before selecting new funds. It atomically publishes exact signed bytes, the complete allocation-to-vout mapping and its owning wallet stage. Pay, forfeit and operator dispositions remain distinct; the latter two have no customer vout. Carrier versions cannot reprice an allocation or silently change its retirement closure. [Atomic handoff][S19].

An ambiguous or lost `COMMIT` retains the exclusive owning-wallet guard, fee reservations, complete group and signed carrier. Recovery waits behind the existing carrier lock and probes/retries publication of **the same bytes**. It does not construct another principal payment because an RPC timed out. Cancellation of the prepare future also retains the staged publication. [Publication recovery][S20].

After complete readback, direct delivery validates all retained versions and their exact authenticated outputs. A monotonic generation frontier rejects a stale delivery object before observation or submission. Recovery must reload the complete owning wallet and journal. It cannot use wall-clock order or “latest output to this script” to choose a winner. The actual active-chain confirmation of any retained version determines the winner, including an older version. Fee guards release only after the owning wallet has synced the confirmed winner and its graph. Startup hydrates recorded winners as well as pending groups, so a restart before wallet synchronization does not free their inputs. [Signed-version validation][S21], [delivery][S22].

The direct tick can construct a higher-fee retained version when the regular estimate rises. It first checks all versions for a chain winner, preserves original backing, recipients and allocation, and applies the same publication, cash and allowance checks. The replacement must increase the largest retained absolute fee by its signed weight times the greater of the configured and Core incremental relay rates. Core access to `getmempoolinfo` is required; missing relay evidence, history capacity or affordable fees defers construction. Neither mempool eviction nor timeout authorizes another principal payment. Replacements do not debit customers again.

Independent history lives under `direct-expiry-witness` in the configured captaind data directory. It binds network/server identity, raw transactions, allocation and carrier hashes. Both trusted daemons must be able to read **and append** this same history. Files and index updates are fsynced before network submission and before recognizing confirmation. Missing, conflicting, corrupt, inaccessible or rolled-back history causes refusal, not a fresh payment. Captaind checks history before workers even when direct scheduling is disabled. [Independent history][S23], [startup ordering][S24].

This detects database-only rollback relative to retained history. It cannot detect jointly rolling PostgreSQL and history back to the same old point. Losing source/WAL history can also lose unpaid rights that aggregate recipient outputs cannot reconstruct. Back up history independently, retain every signed version and preserve the source database/WAL. The history and database can contain secret unlock material or preimages; protect them as financial secrets.

## Returning clients

A frozen or merely broadcast allocation is not reported as paid. Its value remains in the wallet balance, but the current status can still label it spendable while the server refuses cooperative use with the distinct frozen reason. A separate usable-versus-reserved client representation remains required; preserving value is not proof that it is usable. Once the exact mapped carrier is recorded confirmed and still matches its active-chain block, status can truthfully report `Spent` at one confirmation. Legacy `sweep_min_confs=100` does not govern this new route. A deeper network confirmation policy needs explicit runtime qualification. [Status mapping][S25].

`Spent` establishes Ark retirement, including a forfeiture. It does not itself identify a customer payment, destination, miner fee or original payment time. Local adoption records the full Ark debit atomically and idempotently, respecting local locks. Native BIP84 on-chain sync discovers an actual receipt separately. Unknown status, stale confirmation or an unreachable server preserves the unresolved right. The single-ID status RPC revalidates its complete group; large-group status cost remains a performance qualification requirement. [SDK adoption][S26], [debit storage][S27].

A pending board can authenticate status through its retained genuine co-sign proof even when no ordinary registered VTXO row exists. Confirmed direct retirement lets the original wallet finish the saved board action without registering consumed backing. Preserve that proof with settlement history.

Saved arkoor sends distinguish an input-owner refund before registration from the recipient's right after registration, including a lost registration reply. Registration validates every supplied signed chain before returning authenticated confirmed retirement. The sender checks a settled recipient output against its saved signed identity without deriving the recipient key from its own seed; its own change still requires strict seed recovery. Persistent consumed-output tombstones prevent mailbox or round replay from resurrecting retired coins. The delegated-round client also matches every signed output to its requested policy and amount before releasing forfeits; database row order is not a payment contract. [Saved actions][S41], [pending board status][S42], [round reconciliation][S43].

These mechanisms do not prove every interrupted receive, delegated or conditional action terminates. Retain signed claim artifacts and reconcile their independent rights after a crash or database rollback. An unresolved original or replacement cannot be erased because its ancestor was spent.

## Operator setup

The following is a **fresh-state signet configuration procedure**, not evidence that the release is qualified. Use mutually compatible captaind, watchmand, SDK, bark and barkd artifacts. Verify exact source stamps, executable hashes, interpreter/runtime dependencies and network identity on their actual operating hosts. A server-only package does not provide client executables.

Use Bitcoin Core 31 or later with `txindex=1`, synchronized on the same network. Any supported reverse-spend operation requires synchronized `txospenderindex`; its helper refuses an incomplete index. The retained helper is not an active universal recovery path and does not establish automatic recovery after a foreign winner consumes frozen backing. Run only one active captaind per database. This is an operator requirement: the earlier singleton lock was removed. Payment guards and flux locks are process-local; multiple active captaind instances are unsupported. Protect PostgreSQL, Core and Lightning credentials. Admin RPC is unauthenticated privileged access: bind it to loopback or disable it. [Core checks][S28], [inventory/admin API][S29].

Both daemons must select the same settlement route before financial workers start. The first worker records its choice in the database's immutable `expiry_route` row; the other refuses a mismatch even when there are no frozen allocations yet. For direct settlement, enable captaind's direct producer, disable its legacy producer and enable Watchmand's direct mode. Retain the selected route across restart. Do not modify the row to switch architectures: drain and reconcile the existing obligations with their compatible build, stop the old writers, archive the state and use fresh state. This protects matching current binaries; it is not a global singleton guard or protection against an obsolete executable ignoring the contract.

Configure Watchmand to load the original captaind mnemonic and the same server key, while its wallet uses the separate Watchman derivation. Give both trusted services access to the same independently backed-up history; owner-only permissions or a different container UID can otherwise prevent Watchman append.


Before starting financial operation, replace all placeholders, verify signer/destination/network identity, approve actual fee limits, fund the separate wallet roles and complete the release gates. Provision separate whole eligible UTXOs for ordinary selection and the declared urgent floor; sufficient aggregate balance alone is insufficient. Do not derive that fee address from the Rounds descriptor or treat `sweep_address` as proof that Watchman has funds. Seed custody and the surplus destination must remain under operator control.

When the route is qualified, add the Watchmand direct block and set captaind `direct_expiry.enabled=true`, keeping legacy disabled. Start captaind first and wait for successful admin `wallet-inventory` before starting watchmand. This proves the application has completed database initialization, rather than merely that its process exists. Concurrent raw startup against a migrating database is unsupported. Then check Watchmand admin readiness, loaded policy/history and owning-wallet inventory. The service commands are:

```sh

captaind -C /etc/ark/captaind.toml start
captaind rpc --addr 127.0.0.1:3536 wallet-inventory
watchmand -C /etc/ark/watchmand.toml start

```

Wallet inventory does not reveal addresses, mutate the wallet or export private keys. Captaind reports the owning Rounds wallet; Watchmand reports the owning Watchman wallet. Each response explicitly lacks other financial sources and is not a global readiness attestation. Its `pending_transactions`, immediate `pending_parents` and explicit `unavailable_parent_txids` cover only the canonical owning-wallet graph. Public `bitcoin-stripped-body-v1` bytes preserve txids but omit witnesses; the reported signed weight is separate evidence. Nonempty pending scriptSig material or unsafe/missing parents refuse completeness. Do not count pending change alongside its confirmed inputs or mistake wallet locks for additional assets. It is bounded to 2,000 rows/2 MiB and refuses oversized output. Watchmand does not implement the older `WalletStatus` RPC; use its actual `wallet-inventory` endpoint. [Inventory contract][S29].

## Operation, pause and restore

Monitor current Core/owning-wallet tips, scheduler deferral reasons, unresolved source dependencies, signed generations, publication uncertainty, exact mempool/confirmed winners, fee reservations and history append health. Discovery rotates blocked anchors so unrelated supported cuts can progress. A group over 10,000 rows/16 MiB refuses as a whole. Pending group IDs are enumerated completely in bounded pages from one consistent snapshot; the page size no longer rejects the entire backlog. Hydration still covers all retained fee reservations before selection, and no partial group is authorized. Large-load latency and memory qualification remain required. An unavailable node is a supported wait/recovery condition, not completed liveness. Retained legacy payout rows refuse direct startup before workers. [Discovery][S32], [bounded delivery runtime][S18].

Declare available operating capital and a supplemental-fee allowance before admission. Reconcile physical on-chain assets, channel assets and source liabilities separately. Do not count channel funding again alongside channel balances, virtual descendants again alongside their backing, or internal fees/forfeits as new external income. Check:

```text
opening physical assets + external receipts + declared capital injections
= closing physical assets + external payments + miner/router costs
```

Track Watchman subsidy `W-C`, miner fee `M`, customer charges, forfeits and operator surplus separately. The direct ordinary allowance and whole-input cash floor enforce their stated scope. They do not prove capital sufficiency, protect every urgent obligation or enforce cumulative costs across all spenders. A quiet signed fee cap is useful but insufficient for operating readiness. Choose ordinary and pool lifetimes, batching and all exit/claim/grace margins explicitly per network. A 48-block signet example is not a mainnet policy or proof that every Lightning route fits its claim window. For the mainnet operating policy, use at least 4,320 blocks and 10–15 minute round batching, and verify that lifetime exceeds twice the exit margin plus exit delta plus refresh threshold with room to spare. The route does not enforce that mainnet checklist automatically.

Pause new ingress and admission before a declared maintenance window. Stopping both financial services also stops their protective work; it is not a safe universal pause for active deadline-bearing rights. Reconcile accepted requests and choose the supported maintenance action against those deadlines, retaining Core observation, backups and all financial records. Do not abandon, clear or replace signed obligations. A cap discovery disable stops new freezes but does not cancel retained Watchmand deliveries. There is no claim here of a new durable global stop/readiness framework. Restart requires the same history/identity checks and explicit review of any uncertain publication.

Back up the original operator mnemonic, both wallet changesets, complete PostgreSQL base backups and WAL, source/admission/settlement tables, every direct allocation/carrier/mapping, independent history and all three ordinary-fee files. Back up history outside the PostgreSQL rollback domain. Keep configuration, network and destination identity with the backup. Encrypt it, restrict access and verify that both services can append after restore without exposing raw preimages or keys in monitoring.

Restore with both services stopped. Use a complete matching base/WAL recovery and the original seed; restore independent history from its retained newest backup rather than resetting it to a database checkpoint. Verify source identity and wallet roles. Then start in the captaind-ready→watchmand order and let startup validation compare all history and ordinary-fee adoption with complete authenticated signed-version readback. If it refuses, keep financial services stopped and reconcile the discrepancy against retained signed bytes and actual Core confirmation. A full synchronized reverse-spend index may provide actual spender bytes, but does not reconstruct missing unpaid source authority. Do not create an empty witness, remove a conflicting entry, mark a row paid/canceled manually or change the immutable customer destination to make startup pass.

No migration is supplied from old mutable records, custom coin-key payouts or historical MAX-sequence hArk contracts. The producer now uses ZERO sequence to match reconstructed arkoor genesis; this changes txids/signature contracts, enables opt-in RBF and activates BIP68 with zero relative delay. It is a fresh-contract correction, not permission to relabel old signed transactions. Drain/reconcile old obligations with compatible software before a fresh database/identity cutover. Existing legacy nursery recovery and witness protections remain relevant to those obligations. [Contract correction][S33].

## Application and qualification boundaries

BOLT11 `description_hash` is an exact SHA-256 commitment, mutually exclusive with description text. The server and SDK check it against the owning node's invoice. A dedicated authenticated forwarding service can bind it to exact LNURL metadata for the configured Noah domain. This identifies invoice metadata, not entitlement ownership. The recipient's proven account origin remains authoritative. This is the inbound invoice-description commitment; it does not add a strict outbound LNURL metadata verifier to ordinary payment defaults. The forwarding service must protect its own credentials/custody and cannot substitute a server-known mailbox private key. Forwarder authentication, independent external-wallet restoration and operator-facing readiness require separate qualification. This manual defines the Bark API seam; it does not qualify an external wallet application. [Metadata commitment][S34].

### Qualification limits

The implementation is not production-qualified. Selected unit, native and application regressions establish only the exact build and behavior they execute. Historical results do not automatically qualify new bytes. A release must prove its actual ownership, backing consumption, signed transaction validity, restart recovery, original-client completion, seed-only receipt spending, fee stress, load bounds and independently conserved accounting on matching deployed artifacts.

Outstanding safety and liveness limits include the bypassed urgent claims/progression; unbounded incoming hold-node observation under financial locks; recovery after a foreign confirmed spend invalidates a frozen cut; complete conditional-source progression and grant/original retirement; receive-grant association across its crash boundary; granted-receive cancellation/refund timing; frozen value still shown usable; and cumulative fee enforcement outside the ordinary direct signer. Source refusal preserves rights but does not prove eventual payment. A known preimage is not by itself proof of recipient collection, nor permission to block an unrelated no-grant refund.

Retain current-chain confirmation checks without claiming a new reorg subsystem. Database-only rollback detection depends on retaining independent history; joint rollback is outside that guarantee. The operator singleton rule, exact financial artifact identities, adequately backed liabilities and explicit network/capital policy remain requirements. Do not replace missing evidence with a manual settled flag, assume an ancestor spend settled every descendant, or reduce the release scope to whichever source currently pays.
