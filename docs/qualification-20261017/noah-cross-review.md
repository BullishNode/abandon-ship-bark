# Independent source review of qualification_noah.rs

Read-only review; no source edit, build, metadata or runtime. This fixture is a native SDK forwarding prerequisite, not a stock Noah/LNURL execution. Compilation and execution remain NOT RUN.

The SDK and proxy APIs match current source: mailbox proxy forwards an authentic PostArkoorMessage request; blocked calls return Unavailable before forwarding; receive progression persists Delivering after signed outputs are registered; `try_claim_lightning_receive(...,false)` returns at a durable retry/park; repeated manual observations do not spawn an autonomous retry worker. Both SDK daemons are explicitly stopped and joined. The original recipient is dropped before payment and never reopened. Original provider is dropped before opening its same SQLite state with `run_daemon:false`. The platform persister uses the same `db.sqlite` path as BarkSdkBuilder; cached authenticated registration permits the reopen without a new payout-address override or onchain instance. Delivery completion does not require an onchain wallet.

The checkpoint oracle is meaningful: exact signed recipient-policy outputs, sum net of actual configured receive fee, actual product registration/Spendable state, valid native signatures/backing, provider lacks recipient signing keys, and provider has no spendable or claimable receive credit. Reopening must retain the exact Delivering phase/movement ID/serialized outputs. After successful mailbox delivery, the durable checkpoint clears, one successful externally directed movement has zero provider balance effect, and repeated settled-claim calls do not dispatch again.

One valid P2 oracle issue was reported to root and owner: the initial gate stored only signed output bytes, so a successful post to the wrong mailbox could pass. The owner has now changed it to retain `(request.blinded_id,request.vtxos)` and compare the exact recipient-address ServerMailbox ID captured before absence. That source revision closes the identified destination blind spot without waking the recipient.

An initial antiDoS-blocker report from this reviewer was **incorrect and retracted**. `prepare_lightning_receive_htlcs` catches failure to generate an owned-VTXO proof and sends None; server rejects None only when `ln_receive_anti_dos_required` is true. The existing TestContext default is false. The owner explicitly pins that existing false profile. No additional proof board, artificial token or financial row is needed. Production profiles requiring antiDoS admission remain outside this fixture.

Scope of delivery credit: one successful actual upstream post after an outage that rejects before posting, durable checkpoint recovery, and no repost after local settled state. The product deliberately permits replaying the same signed outputs after a crash between successful upstream post and local completion; this test does not inject that lost-ACK window or establish globally exactly-once transport. Server-side mailbox deduplication and absent-recipient economic fallback are separate requirements. Stock Noah callback behavior, strict LNURL metadata hash, native external receiver payout/recovery and production readiness receive no credit here.

No further definite API/lifecycle blocker was established by source review. Updated mailbox destination assertions still require real compilation/execution on root's declared candidate.
